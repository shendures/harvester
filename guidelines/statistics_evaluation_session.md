## 2. 현재 동작 (이 세션이 끝난 시점의 코드 기준)

### 2.1 무엇을 보는가 — 5개 평가 축, 지표별 2단계 게이트

통계 화면의 카드 하나가 평가 축 하나에 대응합니다. 지표마다 분모가 달라 표본 크기를 따로
판단합니다. 최소 수집 횟수는 **축이 아니라 지표별**로 두며, "판정 시작"(그전엔 값·구간만 계산해
두고 등급은 `보류`)과 "`문제` 확정"(그전엔 절대 판정이 `문제`여도 `주의`로 낮춰 표시) 두 단계로
나뉩니다. 근거는 §3.9 참고.

| 평가 축 | 출처 카드 | 판정 지표 | 주의 / 문제 (절대 기준) | 분모 | 판정 시작 | `문제` 확정 |
|---|---|---|---|---|---|---|
| 연결 안정성 | 응답 결과 구성 | 연결 실패율 | 5% / 20% 이상 | 응답 | 1회(§3.14 변경) | 3회(단, 100%는 즉시) |
| 응답 정상성 | 상태 코드 분포 | 접근 차단율(403·429) | 5% / 20% 이상 | 응답 | 1회(§3.14 변경) | 2회 |
| 응답 정상성 | 상태 코드 분포 | HTTP 오류율 | 10% / 30% 이상 | 응답 | 1회(§3.14 변경) | 3회 |
| 수집 성과 | 응답 결과 구성 | 빈 응답률 | 30% / 60% 이상 | 응답 | 1회(§3.14 변경) | 2회(단, 100%는 즉시) |
| 응답 성능 | 응답 속도 구간 | 지연 응답 비율(느림+매우 느림) | 30% / 60% 이상 | 응답 시간이 기록된 응답 | 1회(§3.14 변경) | 3회 |
| 데이터 품질 | 데이터 처리 | 유효 데이터 비율 | `정상` 95% 이상(관측값) / `주의` 95% / `문제` 80% **미만**(신뢰구간) | 추출된 행 | 1회(§3.14 변경) | 2회(단, 전 행이 빈 행이면 즉시) |
| 데이터 품질 | 데이터 처리 | 페이지당 수집량 | 회차 간 편차 10% / 30% (절대 기준 없음) | 회차 | 3회(=`PATTERN_MIN_SESSIONS`) | 3회 |

**판정에 쓰지 않는 KPI**: 응답 성공률(HTTP 오류율·연결 실패율과 완전 중복), 처리량·평균 응답(사이트·설정마다
정상 범위가 달라 절대 기준의 근거가 없음 — 상세 보기에 참고값으로만 표시).

**유효 데이터 비율 임계값**: 관측값(점추정) 95% 이상이면 신뢰구간 없이 정상, 95% 미만이면
Wilson 신뢰구간으로 주의/문제/보류를 가른다. 임계값 95%/80%는 빈 행 허용 오차 5%/20%를 의미하며
연결 실패율·접근 차단율의 기준과 일치한다 — 근거는 §3.12.

**유효 데이터 비율 집계**: 값이 하나라도 있는 행 수 ÷ 추출된 행 수. `None`, 공백 문자열,
`null`·`None`·`N/A` 문자열은 빈 값으로 본다. 일부 필드만 빈 행은 분자에 포함하며, 모든 필드가
빈 행과 필드가 없는 행은 제외한다. `non_empty_rows` 기록이 없는 과거 응답은 새 방식으로
재계산할 원본이 없으므로 이 지표의 분자·분모에서 제외한다. 다른 지표에는 그대로 포함한다.

### 2.2 어떻게 판정하는가

```
① 판정 범위      최근 5회 수집(진행 중·중단 포함)의 응답만 본다. KPI 카드·차트는 그대로 초기화 이후 누적.
② 절대 판정      지표별 Wilson 95% 신뢰구간. 구간이 임계값 한쪽에 온전히 놓일 때만 등급을 매기고 걸치면 "보류".
③ 문제 확정 게이트 절대 판정이 "문제"여도 수집 횟수가 그 지표의 확정 기준(2.1절 표)에 못 미치면
                 "주의"로 낮춰 표시(`capped`)한다 — 세션 하나의 이상만으로 최고 등급을 단정하지 않기 위함.
                 표본 전체가 그 지표에 해당하면(연결 실패·데이터 누락 100%) 게이트 없이 즉시 확정.
④ 패턴 판정      완료된 수집이 3회 이상이면 회차별 값이 일정한지 본다.
                 비율 지표 = 동질성 카이제곱(통계) AND 회차 간 편차 10%p 이상(실질) 일 때만 불안정.
                 페이지당 수집량 = 편차가 자체 노이즈의 6배 초과 AND 10% 이상.
⑤ 결합 규칙      패턴이 일정하면 절대 "주의"여도 정상. 다만 절대 "문제"는 일정해도 문제(안전망).
                 불안정: 편차 10%p↑ 주의, 30%p↑ 문제(문제는 더 엄격한 유의수준 99.5%까지 넘을 때만).
⑥ 시리즈 밖 응답  진행 중·중단 수집의 응답이 절대 판정을 끌어올린 부분은 사면하지 않는다.
⑦ 종합 등급      지표 중 가장 나쁜 등급. 전부 보류면 "대기".
⑧ 최근 악화      최근 100건 vs 이전 구간의 정상 수집률을 2-표본 비율 z-검정(각 구간 30건 이상). 창으로 자르지 않고 전체 이력 기준.
```

각 지표의 확정 게이트는 `PATTERN_MIN_SESSIONS`(3) 이하로만 두므로, ④ 패턴 판정이 적용되는
시점(완료 수집 3회 이상)에는 `capped`가 항상 해제된 상태다 — ③과 ⑤의 사면(absolve) 로직이
서로 섞이지 않는다(불변식, `MetricVerdict.capped` 독스트링 참고).

- 정상: "수집이 정상적으로 진행되고 있습니다. 최근 N회 수집 결과가 일정합니다."
- 정상이지만 일정한 값이 절대 기준을 넘음: "최근 N회 수집 결과는 일정하지만 절대 기준을 넘는 값이 있습니다 — {지표} {값}(주의 {기준}). 사이트의 원래 특성인지 확인하세요."

## 3. 작업별 상세

### 3.1 5개 카드 KPI 통계 평가

- **배경**: 기존 `diagnose()`는 응답 결과 구성 3항목과 접근 차단만 보고, 요청·응답·데이터 처리·응답 속도 KPI는 화면에만 있고 판정에 없었다. 표본 크기도 `총 응답 < 10` 전역 게이트 하나뿐이라 12건 중 3건 실패 같은 무의미한 표본에서도 "문제"로 단정했다.
- **변경**: `diagnose()`를 `evaluate()`로 교체. Wilson 점수 신뢰구간(`_wilson_bounds`), 회차 내 페이지 간 변동(사분위 분산계수 — 이후 3.3에서 교체), 최근 악화 검정(`detect_regression`). 지표 임계값은 `MetricSpec`에 한곳으로 모으고 상세 보기 팝업(`_open_diagnosis_popup`)을 신설.
- **결정(사용자)**: 배너 확장 + 상세 보기 팝업 / 누적 + 최근 악화 감지 / 신뢰구간 기반.
- **효과 예**: 연결 실패 2/10은 단순 비교로는 20%라 "문제"였으나 신뢰구간 하한 5.7%라 "주의".

### 3.2 축별 수집 횟수 게이트

- **배경**: 응답을 아무리 많이 모아도 한 번의 수집이면 독립적인 관측이 아니다. 사용자가 데이터 품질에서 이를 지적했고, 검토 후 전체 축으로 확대.
- **변경**: `AXIS_MIN_SESSIONS`(연결·응답 1회 / 수집 성과·응답 성능 2회 / 데이터 품질 3회). 게이트에 걸린 지표는 **값·신뢰구간은 계산해 두고 등급만 보류**(KPI 카드와 어긋나지 않게). 진행 중 수집을 1회로 셈(세션은 완료 시점에 기록되므로).
- **결정(사용자)**: 축별 차등, 모든 수집 이력 기준, 최근 악화 감지에는 게이트 없음.

### 3.3 회차별 패턴 분석 전환

- **배경**: 게이트의 취지는 "여러 번 수집해 패턴이 일정한지 보는 것"인데 회차 개수만 세고 있었다. **실제 이력(스타벅스 4회)이 모든 값이 동일한데도 배너가 `주의`**였다 — 회차 내 페이지 간 편차(서울 710건↔세종 35건)가 임계값을 넘겨서.
- **변경**: 응답을 `timestamp`로 세션 구간에 귀속(`url_map["session"]`이 항상 1이라 쓸 수 없음), 회차별 집계(`SessionTally`), 비율 지표는 동질성 카이제곱(Wilson–Hilferty 근사, scipy 없이) + 실질 편차. 회차 내 "수집량 편차"를 회차 간 "페이지당 수집량"으로 교체. 완료된 수집 3회부터 패턴 판정.
- **결정(사용자)**: 일관성 우선 + `문제` 안전망 / 단일 수집 항목 전제(다중 항목은 추후) / 패턴 시작 3회.
- **결과**: 실제 이력 배너 `주의`→`정상`, 연결 실패율 `보류`→`정상`.

### 3.4 배너 감사

패턴 기반 종합 평가로서 역할을 하는지 시나리오와 몬테카를로로 확인했다. 잘 되는 것은 실제 이력 정상 판정, 회차당 100건에서 큰 이상 96~100% 검출, 안정 수집 91~97% 정상 유지였고, 결함 7건이 나왔다.

| 감사 | 문제 | 상태 |
|---|---|---|
| #1 | 누적 고착 — 과거 이상 1회가 이후 27회 연속 정상이어도 `문제` 유지 | 해결(3.6) |
| #2 | 페이지당 수집량 오탐이 회차 수에 따라 증가(σ=3%: 3회 5%→40회 95%) | 해결(3.6) |
| #3 | 진행 중 수집의 실패를 패턴이 가림(직전 변경의 회귀) | 해결(3.5) |
| #4 | 일정하지만 나쁜 값(HTTP 오류 25% 등)에 "정상적으로 진행" 단정 | 해결(3.7) |
| #5 | 회차당 16건일 때 통계 부정확 | 해결(3.8, **진단 정정**) |
| #6 | 어느 회차가 이상인지 모름 / 정상 문구에 근거 수치 없음 / 개선·악화 방향 없음 | **미진행** |
| #7 | 회차 귀속으로 집계 비용 약 2배(100,000건 223ms/3초) | 3.6에서 상당 부분 해소(145ms) |

### 3.5 감사 #3 — 진행 중 실패 은폐 수정

- **원인**: 패턴 시리즈에는 완료된 회차만 들어가는데 패턴이 "일정"이면 절대 판정을 덮어썼다.
- **변경**: `_unpatterned_floor()` — 전체 응답 기준 절대 등급이 완료 회차만의 절대 등급보다 나쁠 때만(= 시리즈 밖 응답이 끌어올렸을 때만) 그 등급을 바닥으로 둔다. `MetricVerdict.live` 표시. 이력이 일정하게 절대 `주의`인 경우는 새 수집이 시작돼도 흔들리지 않는다(깜빡임 없음).
- **결과**: 완료 5회 안정 + 진행 중 연속 연결 실패 10건에서 `정상`→`주의`(패턴 도입 전과 동일).

### 3.6 감사 #1·#2 — 최근 5회 창 + 수집량 노이즈 보정

- **#1 창**: `_evaluation_window()`가 최근 `PATTERN_WINDOW`(5)회 수집의 가장 이른 시작 시각 이후 모든 응답을 판정 대상으로 잡는다(`EvalWindow`). 시간 기준이라 중단된 수집의 응답도 5회가 지나면 자연히 빠진다. 회차 귀속을 카드용 전체 순회에서 창 집계로 옮겨 비용도 줄였다. **결정(사용자)**: 창 5회.
- **#2 수집량**: 편차가 회차 간 자체 노이즈(`_noise_scale` — 연속 차이 중 작은 쪽 절반의 평균)의 `YIELD_NOISE_K`(6)배를 넘고 10% 이상일 때만 불안정. 시뮬레이션으로 값을 정했다(σ=3%·창 5회 오탐 12.6%→3.6%, 마지막 회차 −25% 검출 99%, −12% 검출 79%).
- **결과**: 3회차만 빈 응답 50% → 이상이 창에 남는 동안 `문제`, 창에서 빠진 8회부터 `정상`, 30회 시점 `정상`.

### 3.7 감사 #4 — 일정하지만 절대 기준을 넘는 값의 고지

- **변경**: `MetricVerdict.absolved`(절대 `주의`였으나 패턴이 일정해 정상이 된 지표). 등급 결정 코드는 무수정, 배너가 "정상적으로 진행" 대신 위 2.3의 문구로 밝히고 팝업 칸이 `일정·기준 초과`로 표시된다. 배너가 다른 이유로 `주의`·`문제`일 때는 배너에 붙이지 않고 팝업 행에만 표시.
- **결정(사용자 기존 결정 유지)**: 등급 라벨은 초록 `정상` 그대로.

### 3.8 감사 #5 — 진단 정정과 `문제` 엄격화

- **감사의 원인 진단이 틀렸다.** "카이제곱 근사가 기대 빈도 5 미만에서 부정확해 빨간 오탐이 생긴다"고 했으나 시뮬레이션에서 현재 근사 검정의 실제 오탐 크기는 1.7~3.2%로 명목 2.5%에 가까웠다. 정확 검정으로 바꿔도 오탐은 거의 줄지 않고 연결 실패 1→15%(n=16) 검출력은 34%→16%로 반토막, 비용은 지수적이었다. 최소 기대 빈도 가드는 회차당 16건 거의 전부를 보류시켜 패턴을 무력화한다. **둘 다 기각.**
- **진짜 원인**: ① `문제`의 근거가 `주의`와 같아 회차당 16건에서는 유의하면 편차가 거의 항상 30%p를 넘는다 ② 한 회차에만 생긴 작은 이상의 낮은 검출력은 데이터의 한계.
- **변경**: `문제`에만 더 엄격한 유의수준(`CONFIDENCE_Z_STRICT` 2.576). `주의` 이상 집합은 무변경(무작위 60,000 시리즈에서 확인: `문제`→`주의` 강등 2,127건, 그 외 변화 0). 회차당 응답이 30건 미만이면 상세 보기에 검출력 한계를 고지(`small_sample_text`).
- **결과**: 지표 하나의 빨강 오탐 0.53/1.12/2.53%→0.20/0.27/0.30%, 배너 전체(회차당 16건) `문제` 1.8→0.3%(3회)·1.4→0.5%(5회).
- **절충**: 회차당 16건에서 큰 이상의 `문제` 판정률이 11~13%p 내려가나 `주의` 이상 검출은 동일(등급이 한 단계 낮아지는 것).

### 3.9 지표별 2단계 게이트(판정 시작 / `문제` 확정)

- **배경**: 3.2의 축별 게이트(`연결 안정성`·`응답 정상성` 1회 / `수집 성과`·`응답 성능` 2회 /
  `데이터 품질` 3회)를 다시 감사한 결과, 시스템 전체의 "회차 패턴이 일정해야 신뢰한다"는 설계
  철학(`PATTERN_MIN_SESSIONS`=3)보다 게이트가 낮은 축이 4개 있었다 — 이 축들은 세션 1~2회
  시점에 패턴 검증(3.3)을 한 번도 거치지 않은 채 절대 판정만으로 `문제`까지 확정될 수 있었다.
  세션 1회 응답이 아무리 많아도 그 세션의 프록시·네트워크 상태 같은 공통 원인을 공유하는
  군집(cluster) 표본이라, 신뢰구간이 좁게 나와도 "그 세션만의 일시적 현상"과 "구조적 문제"를
  구분하지 못한다는 점은 3.2의 원래 문제의식과 같다.
- **변경**: 게이트를 축이 아니라 지표(`MetricSpec`) 단위로 재정의하고, "판정 시작"
  (`min_sessions` — 그전엔 값·구간만 계산해 두고 등급은 `보류`)과 "`문제` 확정"
  (`min_sessions_problem` — 그전엔 절대 판정이 `문제`여도 `주의`로 낮춰 `MetricVerdict.capped`로
  표시)를 분리했다. 지표별 값과 근거는 2.1절 표 그대로이며, 요약하면:
  - **연결 실패율·HTTP 오류율**(확정 3회): 세션(프록시·네트워크) 종속성이 가장 크고 원인이
    구조적/일시적으로 섞여 있어 재현성을 담보 못 함 → 패턴 검증까지 대기.
  - **접근 차단율**(확정 2회): 같은 수집 설정에 대한 사이트의 결정론적 반응이라 재현성이 높음
    → 2회 연속 확인이면 충분.
  - **데이터 누락률**(확정 2회): 추출 규칙 붕괴는 결정론적이라 다음 세션에도 그대로 재현됨.
  - **유효 데이터 비율**(시작 1회, 확정 2회 — §3.11에서 완화): 아래는 완화 전(시작 2회·확정 3회) 근거로,
    값이 하나라도 있는 행 기준으로 바뀐 뒤에는 자연 변동이 작아 적용되지 않는다. 기존 근거: 콘텐츠 구성에 따른 자연 변동이 커 1회차
    단독 판단은 오탐 위험이 있어 최소 비교점을 확보.
  - **페이지당 수집량 편차**: 정의상 회차 비교 전용 지표라 `PATTERN_MIN_SESSIONS`를 그대로
    참조 — 별도 수치가 아니라 상수 재사용으로 "왜 3인지"를 명확히 함.
  - **지연 응답 비율**(확정 3회): 세션 종속성은 크지만 수집을 막지 않아 긴급성이 낮아 서두를
    이유가 없음.
  - `full_bypass`를 신설해 표본 전체가 그 지표에 해당하면(연결 실패 100%) 데이터 누락 100%
    예외와 같은 원리로 두 게이트를 모두 건너뛰고 즉시 확정하도록 확장.
- **불변식**: 현재 값은 모든 `min_sessions_problem` ≤ `PATTERN_MIN_SESSIONS`(3)이라, 패턴 결합
  (`_with_pattern`)이 적용되는 시점(완료 수집 3회 이상)에는 `capped`가 항상 `False`다 — 3.7의
  사면(absolve) 로직과 섞이지 않는다. 이 값을 벗어나 `min_sessions_problem`을 3 초과로 두면
  이 불변식이 깨질 수 있으니 주의.
- **결정(사용자)**: 게이트 단위를 축에서 지표로 세분화, 2단계(판정 시작/확정) 분리, 확정 전에는
  등급을 낮추되 `capped` 표시로 사실을 숨기지 않음.
- **검증**: `_judge_ratio()` 시나리오 스크립트로 확인 — 연결 실패 90%(n=100)는 세션 1회에서
  `주의`+`capped`, 세션 3회에서 `문제`(capped 해제). 접근 차단 90%는 세션 1회 `주의`+`capped`,
  세션 2회 `문제`. 연결 실패·데이터 누락 100%는 세션 수와 무관하게 즉시 `문제`(회귀 없음 확인).
  헤드리스(`QT_QPA_PLATFORM=offscreen`)로 종합 평가 팝업을 실제로 열어 표·배너·체크리스트 문구가
  예외 없이 그려지는 것도 확인했다.

### 3.10 유효 데이터 비율 — "정상" 판정을 점추정 100% 전용으로 변경

- **배경**: 사용자 요청으로 "유효 데이터 비율"만 `정상`을 관측값 100%일 때로 좁히기로 함.
  기존처럼 `정상`을 신뢰구간(하한 ≥ warn)으로 요구하면, Wilson 신뢰구간 하한은 유한 표본에서
  1.0에 절대 도달하지 못해 `정상`이 사실상 나오지 않는다.
- **변경**: `MetricSpec.exact_ok` 필드 신설(기본 `False`, `SPEC_VALID`만 `True`). `SPEC_VALID`의
  경계값을 `warn=0.90/problem=0.70`에서 `warn=0.99/problem=0.90`으로 조정. `_judge_ratio()`는
  게이팅 다음 단계에서 `exact_ok`이고 `hits==sample`이면 즉시 `정상`, 아니면 기존처럼
  `_ratio_level()`(신뢰구간)로 판정하되 그 결과가 `정상`이면 `주의`로 강제 하향한다 — 표본이
  커지면 관측값이 100% 미달이어도 신뢰구간 하한이 warn을 넘어 `정상`이 나올 수 있는데, 이를
  막기 위함(예: 9990/10000=99.9%는 하한이 0.99를 넘지만 `정상`이 아니라 `주의`).
  `_ratio_level()`·다른 6개 지표는 무수정. 상세 보기 표의 "절대 기준" 칸(`metric_criteria_text`)도
  이 지표만 `"100% / 99% / 90% 미만"` 3단으로 표시.
- **상충 검토(패턴 사면)**: 회차별 값이 일정하게 99% 미만이면 절대 판정은 `주의`이지만, 3.7의
  사면(absolve) 로직이 그대로 적용돼 패턴이 일정하면 `정상`으로 승격될 수 있다 — "100%일 때만
  정상"이라는 이번 규칙과 겉으로는 모순돼 보인다. 사용자에게 확인한 결정: **사면 로직은 무수정
  유지**(일관성 우선 원칙은 별도의 기존 결정이라 이번 변경 범위 밖).
- **결정(사용자)**: 정상은 관측값(점추정) 100% 전용, 주의 99%/문제 90%(신뢰구간)로 재설계.
  사면 로직과의 상충은 인지하되 기존 동작 유지.
- **검증**: 자동 테스트 없음(이 모듈 공통). `_judge_ratio` 순수 로직을 별도 스크립트로 재현해
  손으로 확인 — 100/100(세션 3회) `정상`, 100/100(세션 1회) `보류`(게이트), 9990/10000(세션 3회)
  `주의`(하한 0.99 초과에도 정상 아님, 핵심 회귀 케이스), 85/100(세션 3회) `주의`, 0/0 `보류`.
  `metric_criteria_text(SPEC_VALID)` == `"100% / 99% / 90% 미만"` 확인. `py_compile` 통과. 실제
  GUI(종합 평가 상세 보기 표의 "절대 기준" 칸 문구 길이·잘림)는 WSL에 PyQt6가 없어 미확인 —
  Windows에서 확인 필요.

### 3.11 유효 데이터 비율 — 일부 필드 누락 허용

- **배경**: 아직 전화번호가 없는 매장처럼 일부 필드가 비어 있어도 수집 행 자체는 유용하다.
  기존 `complete_rows`는 이런 행까지 제외해 수집 성공 여부를 과소평가했다.
- **변경**: 새 수집 응답에 `non_empty_rows`를 기록한다. `worker.count_field_fill()`은
  `None`·공백·null 표기를 빈 값으로 보고, 값이 하나라도 있는 행을 센다. KPI와 종합 평가의
  합산·회차별 분자는 새 기록을 사용한다. 과거 `complete_rows`는 의미가 달라 새 비율에
  섞지 않는다. 카드 설명과 원인·조치 문구도 새 기준에 맞췄다.
- **판정 임계값**: 기존 100% / 99% / 90%와 `exact_ok`·회차 패턴 규칙을 유지한다고 했으나, 이후 §3.12에서
  관측값 95% 이상(point_ok) / 95% / 80%로 완화했다.
  새 집계값의 실제 분포(새 방식 수집 5~10회)를 본 뒤 조정할 예정이다.
- **게이트 완화**: `SPEC_VALID`의 판정 시작 2→1회, `문제` 확정 3→2회(데이터 누락률과 동일). 새 정의에서는
  "빈 행"의 자연 발생률이 ~0%라 §3.9의 "콘텐츠 구성에 따른 자연 변동" 근거가 사라졌다.
- **전량 빈 행 즉시 판정**: `SPEC_VALID.full_bypass=True`. `_judge_ratio`의 bypass 조건을 지표 방향에 맞춰
  일반화(`hits == (0 if higher_is_better else sample)`) — 값이 큰 게 좋은 지표는 표본 전체가 해당할 때가
  `hits==0`이다. 루트 XPath는 맞지만 하위 셀렉터가 전부 실패하면 응답은 "정상 수집"이라 데이터 누락률에
  안 잡히므로, 이 지표가 1회차에 바로 `문제`를 내야 한다.
- **검증**: 미실행(Python 실행 미승인). Windows에서 확인 필요 — 0/50(세션 1)→`문제`, 50/50(세션 1)→`정상`,
  0/0→`보류`.

### 3.12 유효 데이터 비율 — 임계값 및 판정 로직 완화

- **배경**: §3.10의 "관측값 정확히 100%만 정상"은 극도로 엄격해, 빈 행 0.03%(3000행 중 1건)도 `주의`를 받았다.
  실측(`stats_history.json` 51응답)에서는 빈 행 0건만 나왔고, 임계값 99%/90%는 실제 분포 근거가 없었다.
  절대 기준이 너무 높으면 회차 패턴의 사면(일정하면 정상) 조건도 겉보기로 모순된다.
- **변경**:
  - **정상 기준**: 관측값 ≥ 95%(point_ok)이면 신뢰구간 없이 정상 — 빈 행 5% 이하는 허용.
  - **임계값**: `warn=0.95 / problem=0.80` — 빈 행 5% / 20%로, 연결 실패율·접근 차단율(각 5%/20%)과 정합.
  - **판정 로직**: 관측값 < 95%일 때만 Wilson 신뢰구간 적용(기존처럼 상한이 warn 미만 → 주의, problem 미만 → 문제, 걸침 → 보류).
  - **코드**: `MetricSpec.exact_ok` → `point_ok`로 개명, `_judge_ratio`의 "100% 미달인데 CI에서 정상" 강제 하향 블록 삭제,
    `metric_criteria_text`의 3단 분기 삭제.
  - **유지**: 게이트(시작 1회/확정 2회), `full_bypass`, 회차 패턴 결합·사면 로직은 무수정.
- **효과**: 
  - 빈 행 5% 이하는 표본 크기와 무관하게 정상(허용 오차).
  - 빈 행이 늘수록 등급이 단조롭게 악화(기존의 비단조 역전 해소).
  - 회차 패턴 사면과의 모순 자연 해소(정상이 관측값 95% 이상으로 낮춰졌으므로 "일정하고 95% 이상"이 달성 가능).
  - 임계값이 경험값이므로 실제 분포 수집 후 조정 가능(타 지표들과 동일 정책).
- **검증**: 자동 테스트 없음(3.10과 동일). 순수 로직 스크립트로 재현 — 95/100·950/1000 → 정상, 80/100(세션≥2) → 주의,
  20/100(세션≥2) → 문제, 90/100 → 보류. `metric_criteria_text(SPEC_VALID) == "95% / 80% 미만"` 확인,
  `py_compile` 통과. PyQt 팝업은 WSL PyQt6 없어 미확인 → Windows에서 종합 평가 상세 보기 "절대 기준" 칸 확인 필요.

### 3.13 `정상` 등급은 수집(JOB) 2회부터 — URL 수가 배너를 좌우하던 문제

- **배경**: 같은 1회 수집인데 '샤브올데이'(URL 1개)는 배너가 `대기`, '파리바게뜨'(URL 17개)는 `정상`이었다. 종합 등급은
  지표 중 가장 나쁜 것을 따르되 `보류`를 최하위로 두므로 지표 하나만 `정상`이어도 배너가 `정상`이 되는데, Wilson 신뢰구간은
  응답이 많을수록 좁아져 응답 1건(상한 0.79)은 전 지표 `보류`, 17건(상한 0.18)은 데이터 누락률(warn 30%)이 `정상`이 된다.
  즉 수집 횟수가 아니라 응답(URL) 수가 배너를 결정하고 있었다. 수집 횟수(`sessions`)는 원래 워커 실행 1회(=수집 대상 1건의
  JOB 1회)당 1이라 URL 수와 무관했다 — 어긋난 것은 횟수 계산이 아니라 `정상`을 표본 크기만으로 매기던 판정이다.
- **변경**: `MIN_SESSIONS_OK = 2` 신설. `_judge_ratio`가 신뢰구간·`point_ok`로 `정상`이 나와도 수집이 2회 미만이면 `보류`로
  둔다. `_first_ok_session(spec) = max(min_sessions, MIN_SESSIONS_OK)`를 `_is_gate_pending`·`_next_gate`가 써서 안내
  문구("수집 2회부터 평가를 시작합니다")가 맞게 나온다. 도움말에도 한 줄 추가.
- **유지**: `주의`·`문제`는 지표별 판정 시작 횟수(대부분 1회)부터 그대로 매긴다 — 연결 실패 100%·유효 행 0건 같은 붕괴를 1회차에
  놓치지 않기 위함. `full_bypass`·`문제` 확정 게이트·회차 패턴 결합은 무수정.
- **검증**: `PyQt6`를 스텁으로 대체해 `_judge_ratio`·`_banner_diagnosis`를 직접 호출 — 1회 수집에서 응답 1건·17건 모두
  `보류`(배너 `보류`), 유효 행 157/157도 `보류`, 2회 수집에서는 `정상`, 연결 실패 100%·유효 행 0/50은 1회에서도 `문제`.
- **배너 등급 변경**: 전 지표가 보류일 때 배너가 `대기`→`보류`로 바뀐다. 수집 기록이 없을 때만 `대기`를 표시하므로,
  `대기`는 "판단할 수집 기록이 아직 없다"(0회), `보류`는 "수집을 1회 진행했으나 판단 보류"로 의미가 갈린다.

### 3.14 수집 횟수 기준 제거 — 수집 1회부터 판정, `MIN_SESSIONS_OK` 폐지

- **배경**: 3.13에서 `MIN_SESSIONS_OK = 2`를 도입해 "정상"을 수집 2회부터 매기기 시작했으나,
  사용자 요청(수집 1회 이상이면 지표 평가 시작)으로 이 기준을 제거한다.
- **변경**:
  - `MIN_SESSIONS_OK` 상수 제거.
  - `SPEC_SLOW.min_sessions` 2 → 1 (다른 비율 지표는 이미 1, `min_sessions` 기본값 1이라 명시값은 생략).
  - `_judge_ratio`의 "정상 → 보류 되돌림" 코드(`if level == DIAG_OK and sessions < MIN_SESSIONS_OK: level = DIAG_HOLD`) 제거.
  - `_first_ok_session(spec)` 함수 제거. `_is_gate_pending`과 `_next_gate`가 `spec.min_sessions`을 직접 사용.
  - 도움말 `diagnosis_help_text`: "'정상'은 수집 2회부터" 및 "수집 1회는 관측 1번이라" 문구를 "수집 1회 이상이면 항목별로 판정"으로 통합.
- **유지**: **"문제" 확정 게이트**(`min_sessions_problem`, 2~3회)는 그대로. 1회차에도 등급을 매기지만
  "문제" 수준이면 "주의(확정 전)"로 표시(`MetricVerdict.capped`). 이것까지 없애면 1회의 일시적 이상이 곧바로 "문제"로 단정.
  **페이지당 수집량**(pattern_only)은 회차 간 비교 지표라 수집 3회 미만에서는 계산 자체가 불가 → 보류 유지.
- **배너 시뮬레이션**: 수집 1회, 연결 실패 0% (신뢰구간 0~3.7%) → "정상", 지표 6개 전부 평가 시작.
  (3.13에서는 신뢰구간이 warn 이상이어도 수집 2회 미만이면 "보류"였음.)

## 5. 정정·실패·주의 기록

작업 중 판단이 틀렸거나 문제가 생긴 지점을 숨기지 않고 남깁니다.

1. **감사 #5의 원인 진단이 틀렸다** — 3.8 참조. 계획 전 시뮬레이션에서 발견해 방향을 바꿨다.
2. **정확 검정 프로토타입이 4분 넘게 걸려 중단** — 기대 빈도가 충분한 경우까지 정확 검정을 돌려 경우의 수가 지수적으로 늘었다(희귀 사건 50개에서 약 31만). 기대 빈도가 충분하면 근사가 맞으므로 하이브리드가 옳다는 근거가 됐다.
3. **기대치를 코드가 아니라 설계 귀결에 맞게 정정한 사례** — #3의 진행 중 연속 실패 30건이 `주의`가 아니라 `문제`(창이 작아져 희석이 줄어 더 민감해짐), 중단 수집 복귀 시 지표는 11회에 정상이나 배너는 12회(최근 악화 검정이 응답 100건 ≈ 6회분 기준이라 1회 더 걸림).
4. **테스트 데이터 산수 오류를 코드 결함으로 오인하지 않으려 지표별 등급을 직접 찍어 확인** — 다중 사면 시나리오가 3번 실패했으나 원인은 데이터(지연 62.5%는 `문제` 근처, 빈 응답 6/16은 Wilson 하한이 기준을 걸쳐 `보류`).
5. **성능 측정 실수** — 람다에서 전체 순회를 두 번 호출해 294ms로 부풀렸다가 재측정(실제 145ms).
6. **지표명 변경을 따라가지 못한 테스트 스크립트** — "회차별 수집량"→"페이지당 수집량"으로 이름을 바꾼 뒤 스크립트가 옛 이름을 찾아 조회 실패(코드 문제 아님).
7. **실제 수집 이력 `stats_history.json` 소실** — 검증 도중 저장소 루트의 이 파일(4회 수집·응답 64건)이 없어졌다. `.gitignore` 대상이라 git으로 복구할 수 없고, 홈·`/tmp`·Windows 마운트에서도 사본을 찾지 못했다. 저장소에 삭제 코드는 없고(쓰기는 `os.replace`뿐) 이 세션의 `DataStore` 사용 스크립트 8개는 전부 저장을 차단했으나 **원인은 확정하지 못했다.** 파일을 임의로 재생성하지 않았고, 이후 회귀 검증은 예전에 기록해 둔 집계로 만든 합성 대체 데이터(테스트 전용)로 대체했다. 필요하면 앱에서 다시 수집해야 한다.

| `BANNER_MAX_CAUSES` | 2 | 배너에 적는 원인 문장 수 |

## 8. 검증 방법과 재현

이 프로젝트에는 테스트 프레임워크가 없어 세션 내내 **`py_compile` + 헤드리스(`QT_QPA_PLATFORM=offscreen`) 스모크 + 스크린샷 + 시뮬레이션**으로 검증했습니다. `ruff`는 환경에 설치돼 있지 않아 변경 심볼의 사용처를 `grep`으로 전수 확인했습니다.

- **회귀 스위트**(창·사면·결합 규칙 24건·게이트·GUI)와 시뮬레이션(오탐률·검출력 몬테카를로)은 세션 임시 폴더에 두었고 **저장소 밖이라 사라질 수 있습니다.** 재사용하려면 저장소의 테스트로 옮겨야 합니다(이 세션에서는 하지 않음).
- 검증 원칙: 등급 결정을 건드리지 않는 변경은 **기존 시나리오의 등급이 그대로인지**를 먼저 확인하고, 통계 규칙은 저장소를 건드리지 않는 프로토타입으로 오탐률·검출력을 먼저 재고 나서 실제 코드에서 같은 수치가 재현되는지 대조했습니다.
- 시뮬레이션은 난수 시드를 고정했습니다(오차는 표본 수 T=600~4,000의 표집 오차 범위).
