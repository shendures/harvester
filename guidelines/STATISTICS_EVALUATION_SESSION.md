```
② 절대 판정      지표별 Wilson 95% 신뢰구간. 구간이 임계값 한쪽에 온전히 놓일 때만 등급을 매기고 걸치면 "보류".
③ 패턴 판정      완료된 수집이 3회 이상이면 회차별 값이 일정한지 본다.
                 비율 지표 = 동질성 카이제곱(통계) AND 회차 간 편차 10%p 이상(실질) 일 때만 불안정.
                 페이지당 수집량 = 편차가 자체 노이즈의 6배 초과 AND 10% 이상.
④ 결합 규칙      패턴이 일정하면 절대 "주의"여도 정상. 다만 절대 "문제"는 일정해도 문제(안전망).
                 불안정: 편차 10%p↑ 주의, 30%p↑ 문제(문제는 더 엄격한 유의수준 99.5%까지 넘을 때만).
⑤ 시리즈 밖 응답  진행 중·중단 수집의 응답이 절대 판정을 끌어올린 부분은 사면하지 않는다.
⑥ 종합 등급      지표 중 가장 나쁜 등급. 전부 보류면 "대기".
⑦ 최근 악화      최근 100건 vs 이전 구간의 정상 수집률을 2-표본 비율 z-검정(각 구간 30건 이상). 창으로 자르지 않고 전체 이력 기준.
```

## 3. 작업별 상세

### 3.1 5개 카드 KPI 통계 평가

- **배경**: 기존 `diagnose()`는 응답 결과 구성 3항목과 접근 차단만 보고, 요청·응답·데이터 처리·응답 속도 KPI는 화면에만 있고 판정에 없었다. 표본 크기도 `총 응답 < 10` 전역 게이트 하나뿐이라 12건 중 3건 실패 같은 무의미한 표본에서도 "문제"로 단정했다.
- **변경**: `diagnose()`를 `evaluate()`로 교체. Wilson 점수 신뢰구간(`_wilson_bounds`), 회차 내 페이지 간 변동(사분위 분산계수 — 이후 3.3에서 교체), 최근 악화 검정(`detect_regression`). 지표 임계값은 `MetricSpec`에 한곳으로 모으고 상세 보기 팝업(`_open_diagnosis_popup`)을 신설.
- **결정(사용자)**: 배너 확장 + 상세 보기 팝업 / 누적 + 최근 악화 감지 / 신뢰구간 기반.
- **효과 예**: 연결 실패 2/10은 단순 비교로는 20%라 "문제"였으나 신뢰구간 하한 5.7%라 "주의".

### 3.2 축별 수집 횟수 게이트

- **배경**: 응답을 아무리 많이 모아도 한 번의 수집이면 독립적인 관측이 아니다. 사용자가 데이터 품질에서 이를 지적했고, 검토 후 전체 축으로 확대.
- **변경**: `AXIS_MIN_SESSIONS`(연결·응답 1회 / 수집 성과·응답 성능 2회 / 데이터 품질 3회). 게이트에 걸린 지표는 **값·신뢰구간은 계산해 두고 등급만 보류**(KPI 카드와 어긋나지 않게). 진행 중 수집을 1회로 셈(세션은 완료 시점에 기록되므로).
- **결정(사용자)**: 축별 차등, 모든 수집 이력 기준, 최근 악화 감지에는 게이트 없음.

### 3.3 회차별 패턴 분석 전환

- **배경**: 게이트의 취지는 "여러 번 수집해 패턴이 일정한지 보는 것"인데 회차 개수만 세고 있었다. **실제 이력(스타벅스 4회)이 모든 값이 동일한데도 배너가 `주의`**였다 — 회차 내 페이지 간 편차(서울 710건↔세종 35건)가 임계값을 넘겨서.
- **변경**: 응답을 `timestamp`로 세션 구간에 귀속(`url_map["session"]`이 항상 1이라 쓸 수 없음), 회차별 집계(`SessionTally`), 비율 지표는 동질성 카이제곱(Wilson–Hilferty 근사, scipy 없이) + 실질 편차. 회차 내 "수집량 편차"를 회차 간 "페이지당 수집량"으로 교체. 완료된 수집 3회부터 패턴 판정.
- **결정(사용자)**: 일관성 우선 + `문제` 안전망 / 단일 수집 항목 전제(다중 항목은 추후) / 패턴 시작 3회.
- **결과**: 실제 이력 배너 `주의`→`정상`, 연결 실패율 `보류`→`정상`.

### 3.4 배너 감사

패턴 기반 종합 평가로서 역할을 하는지 시나리오와 몬테카를로로 확인했다. 잘 되는 것은 실제 이력 정상 판정, 회차당 100건에서 큰 이상 96~100% 검출, 안정 수집 91~97% 정상 유지였고, 결함 7건이 나왔다.

| 감사 | 문제 | 상태 |
|---|---|---|
| #1 | 누적 고착 — 과거 이상 1회가 이후 27회 연속 정상이어도 `문제` 유지 | 해결(3.6) |
| #2 | 페이지당 수집량 오탐이 회차 수에 따라 증가(σ=3%: 3회 5%→40회 95%) | 해결(3.6) |
| #3 | 진행 중 수집의 실패를 패턴이 가림(직전 변경의 회귀) | 해결(3.5) |
| #4 | 일정하지만 나쁜 값(HTTP 오류 25% 등)에 "정상적으로 진행" 단정 | 해결(3.7) |
| #5 | 회차당 16건일 때 통계 부정확 | 해결(3.8, **진단 정정**) |
| #6 | 어느 회차가 이상인지 모름 / 정상 문구에 근거 수치 없음 / 개선·악화 방향 없음 | **미진행** |
| #7 | 회차 귀속으로 집계 비용 약 2배(100,000건 223ms/3초) | 3.6에서 상당 부분 해소(145ms) |

### 3.5 감사 #3 — 진행 중 실패 은폐 수정

- **원인**: 패턴 시리즈에는 완료된 회차만 들어가는데 패턴이 "일정"이면 절대 판정을 덮어썼다.
- **변경**: `_unpatterned_floor()` — 전체 응답 기준 절대 등급이 완료 회차만의 절대 등급보다 나쁠 때만(= 시리즈 밖 응답이 끌어올렸을 때만) 그 등급을 바닥으로 둔다. `MetricVerdict.live` 표시. 이력이 일정하게 절대 `주의`인 경우는 새 수집이 시작돼도 흔들리지 않는다(깜빡임 없음).
- **결과**: 완료 5회 안정 + 진행 중 연속 연결 실패 10건에서 `정상`→`주의`(패턴 도입 전과 동일).

### 3.6 감사 #1·#2 — 최근 5회 창 + 수집량 노이즈 보정

- **#1 창**: `_evaluation_window()`가 최근 `PATTERN_WINDOW`(5)회 수집의 가장 이른 시작 시각 이후 모든 응답을 판정 대상으로 잡는다(`EvalWindow`). 시간 기준이라 중단된 수집의 응답도 5회가 지나면 자연히 빠진다. 회차 귀속을 카드용 전체 순회에서 창 집계로 옮겨 비용도 줄였다. **결정(사용자)**: 창 5회.
- **#2 수집량**: 편차가 회차 간 자체 노이즈(`_noise_scale` — 연속 차이 중 작은 쪽 절반의 평균)의 `YIELD_NOISE_K`(6)배를 넘고 10% 이상일 때만 불안정. 시뮬레이션으로 값을 정했다(σ=3%·창 5회 오탐 12.6%→3.6%, 마지막 회차 −25% 검출 99%, −12% 검출 79%).
- **결과**: 3회차만 빈 응답 50% → 이상이 창에 남는 동안 `문제`, 창에서 빠진 8회부터 `정상`, 30회 시점 `정상`.

### 3.7 감사 #4 — 일정하지만 절대 기준을 넘는 값의 고지

- **변경**: `MetricVerdict.absolved`(절대 `주의`였으나 패턴이 일정해 정상이 된 지표). 등급 결정 코드는 무수정, 배너가 "정상적으로 진행" 대신 위 2.3의 문구로 밝히고 팝업 칸이 `일정·기준 초과`로 표시된다. 배너가 다른 이유로 `주의`·`문제`일 때는 배너에 붙이지 않고 팝업 행에만 표시.
- **결정(사용자 기존 결정 유지)**: 등급 라벨은 초록 `정상` 그대로.

### 3.8 감사 #5 — 진단 정정과 `문제` 엄격화

- **감사의 원인 진단이 틀렸다.** "카이제곱 근사가 기대 빈도 5 미만에서 부정확해 빨간 오탐이 생긴다"고 했으나 시뮬레이션에서 현재 근사 검정의 실제 오탐 크기는 1.7~3.2%로 명목 2.5%에 가까웠다. 정확 검정으로 바꿔도 오탐은 거의 줄지 않고 연결 실패 1→15%(n=16) 검출력은 34%→16%로 반토막, 비용은 지수적이었다. 최소 기대 빈도 가드는 회차당 16건 거의 전부를 보류시켜 패턴을 무력화한다. **둘 다 기각.**
- **진짜 원인**: ① `문제`의 근거가 `주의`와 같아 회차당 16건에서는 유의하면 편차가 거의 항상 30%p를 넘는다 ② 한 회차에만 생긴 작은 이상의 낮은 검출력은 데이터의 한계.
- **변경**: `문제`에만 더 엄격한 유의수준(`CONFIDENCE_Z_STRICT` 2.576). `주의` 이상 집합은 무변경(무작위 60,000 시리즈에서 확인: `문제`→`주의` 강등 2,127건, 그 외 변화 0). 회차당 응답이 30건 미만이면 상세 보기에 검출력 한계를 고지(`small_sample_text`).
- **결과**: 지표 하나의 빨강 오탐 0.53/1.12/2.53%→0.20/0.27/0.30%, 배너 전체(회차당 16건) `문제` 1.8→0.3%(3회)·1.4→0.5%(5회).
- **절충**: 회차당 16건에서 큰 이상의 `문제` 판정률이 11~13%p 내려가나 `주의` 이상 검출은 동일(등급이 한 단계 낮아지는 것).

## 5. 정정·실패·주의 기록

작업 중 판단이 틀렸거나 문제가 생긴 지점을 숨기지 않고 남깁니다.

1. **감사 #5의 원인 진단이 틀렸다** — 3.8 참조. 계획 전 시뮬레이션에서 발견해 방향을 바꿨다.
2. **정확 검정 프로토타입이 4분 넘게 걸려 중단** — 기대 빈도가 충분한 경우까지 정확 검정을 돌려 경우의 수가 지수적으로 늘었다(희귀 사건 50개에서 약 31만). 기대 빈도가 충분하면 근사가 맞으므로 하이브리드가 옳다는 근거가 됐다.
3. **기대치를 코드가 아니라 설계 귀결에 맞게 정정한 사례** — #3의 진행 중 연속 실패 30건이 `주의`가 아니라 `문제`(창이 작아져 희석이 줄어 더 민감해짐), 중단 수집 복귀 시 지표는 11회에 정상이나 배너는 12회(최근 악화 검정이 응답 100건 ≈ 6회분 기준이라 1회 더 걸림).
4. **테스트 데이터 산수 오류를 코드 결함으로 오인하지 않으려 지표별 등급을 직접 찍어 확인** — 다중 사면 시나리오가 3번 실패했으나 원인은 데이터(지연 62.5%는 `문제` 근처, 빈 응답 6/16은 Wilson 하한이 기준을 걸쳐 `보류`).
5. **성능 측정 실수** — 람다에서 전체 순회를 두 번 호출해 294ms로 부풀렸다가 재측정(실제 145ms).
6. **지표명 변경을 따라가지 못한 테스트 스크립트** — "회차별 수집량"→"페이지당 수집량"으로 이름을 바꾼 뒤 스크립트가 옛 이름을 찾아 조회 실패(코드 문제 아님).
7. **실제 수집 이력 `stats_history.json` 소실** — 검증 도중 저장소 루트의 이 파일(4회 수집·응답 64건)이 없어졌다. `.gitignore` 대상이라 git으로 복구할 수 없고, 홈·`/tmp`·Windows 마운트에서도 사본을 찾지 못했다. 저장소에 삭제 코드는 없고(쓰기는 `os.replace`뿐) 이 세션의 `DataStore` 사용 스크립트 8개는 전부 저장을 차단했으나 **원인은 확정하지 못했다.** 파일을 임의로 재생성하지 않았고, 이후 회귀 검증은 예전에 기록해 둔 집계로 만든 합성 대체 데이터(테스트 전용)로 대체했다. 필요하면 앱에서 다시 수집해야 한다.

## 8. 검증 방법과 재현

이 프로젝트에는 테스트 프레임워크가 없어 세션 내내 **`py_compile` + 헤드리스(`QT_QPA_PLATFORM=offscreen`) 스모크 + 스크린샷 + 시뮬레이션**으로 검증했습니다. `ruff`는 환경에 설치돼 있지 않아 변경 심볼의 사용처를 `grep`으로 전수 확인했습니다.

- **회귀 스위트**(창·사면·결합 규칙 24건·게이트·GUI)와 시뮬레이션(오탐률·검출력 몬테카를로)은 세션 임시 폴더에 두었고 **저장소 밖이라 사라질 수 있습니다.** 재사용하려면 저장소의 테스트로 옮겨야 합니다(이 세션에서는 하지 않음).
- 검증 원칙: 등급 결정을 건드리지 않는 변경은 **기존 시나리오의 등급이 그대로인지**를 먼저 확인하고, 통계 규칙은 저장소를 건드리지 않는 프로토타입으로 오탐률·검출력을 먼저 재고 나서 실제 코드에서 같은 수치가 재현되는지 대조했습니다.
- 시뮬레이션은 난수 시드를 고정했습니다(오차는 표본 수 T=600~4,000의 표집 오차 범위).
