## 요약

원래 요청은 "자동 저장이 켜진 대상을 수집했는데 결과가 0건이면 자동 저장하지 말아
달라"는 작은 요청이었습니다. 조사해 보니 그 로직은 이미 있었고, 실제 문제는 "수집"을
눌렀을 뿐인데 "추출 오류" 팝업이 뜨는 등 **어떤 상황에서 팝업을 띄우고 어떤 상황에서
로그만 남길지에 대한 기준이 없었다**는 것이었습니다. 이 기준을 정리하는 과정에서
팝업이 무인 실행(스케줄)의 다음 순번을 막아버리는 것과 같은, 훨씬 심각한 문제 몇
가지도 함께 발견해 이번에 같이 고쳤습니다.

이 앱은 수집을 4가지 방식(수동 실행 한 건, 여러 개 선택 실행, 전체 실행, 예약된 스케줄
실행)으로 돌릴 수 있는데, "결과를 어떻게 알릴지"가 방식마다, 심지어 같은 방식 안에서도
상황마다 제각각이었습니다. 확인된 핵심 문제는 세 가지입니다.

1. **팝업이 다음 작업을 막는다.** 이 앱은 팝업창이 떠 있으면 사용자가 닫을 때까지 다음
   수집이 시작되지 않는 구조입니다. "여러 개를 골라 순서대로 수집"할 때 중간에 저장
   위치가 겹치는 등의 상황을 만나면 팝업이 뜨고, 자리를 비운 사이라면 나머지는 영원히
   시작되지 않습니다.
2. **"실행 실패"를 "사용자가 껐다"로 착각한다.** 프로그램 내부 오류로 수집이 중단됐을
   때와 사용자가 직접 중지 버튼을 눌렀을 때가 코드상 구분되지 않고 있었습니다. 그
   결과 예약된 스케줄이 내부 오류로 한 번 실패하면, 그 스케줄은 다음 실행 예약 자체가
   안 되고 **조용히 영구 정지**했습니다.
3. **문제가 생겨도 아무도 모른다.** 무인으로 도는 스케줄에서 저장이 실패하거나 사이트
   구조가 바뀌어 데이터를 못 가져와도, 로그 파일 한 줄 외에는 아무 표시가 없었습니다.

3단계로 나눠 전부 구현했습니다.

| 순위 | 목표 | 한 줄 요약 | 상태 |
|---|---|---|---|
| 1순위 | 급한 버그 수정 | 실행 실패를 사용자 중단으로 오판해 스케줄이 영구 정지하는 문제, 순차 수집 중 팝업이 다음 작업을 막는 문제 | ✅ 완료 |
| 2순위 | 판단 기준 통일 | "지금 팝업을 띄워도 되는가"를 하나의 규칙으로 정리, 팝업 대신 화면에 남는 "실패 배너" 신설 | ✅ 완료 |
| 3순위 | 안 보이던 것 보이게 | 조용히 묻히던 정보(추출 오류, 저장 실패, 배치 결과)를 로그·트레이 알림으로 드러냄 | ✅ 완료 |

## 1. 핵심 진단

현재 코드는 "팝업이냐 로그냐"를 **`is_unattended`(또는 `silent`) 불리언 하나**로 결정한다.
이 하나가 서로 다른 세 질문을 뭉뚱그리고 있다.

1. 사람이 지금 화면 앞에 있는가 (모달을 *볼* 수 있는가)
2. 이 통보는 질문인가 알림인가 (모달이 *필요*한가)
3. 계속 진행하면 더 나빠지는가 (멈춰야 하는가)

그리고 이 앱에서 모달은 단순 UX 문제가 아니라 **실행 차단 장치**다. 대기 큐를 꺼내는
`_consume_pending_queue()`가 `_on_finished()`의 **마지막 줄**
(`trigger/main_window.py:258` 단일, `:570` 다중)에 있어서, 그 앞에서 `QMessageBox.exec()`가
뜨면 사용자가 닫을 때까지 다음 순번이 시작되지 않는다. 코드 주석도 이를 명시한다
(`trigger/main_window.py:494-495`): *"전체 수집·스케줄 실행은 '무인 흐름' — 모달을 띄우면
사용자가 닫아줄 때까지 다음 순번이 영영 시작되지 않으므로 트레이 알림만 사용."*

**②가 가장 위험하다.** 사람이 방금 버튼을 눌렀다는 이유로 `is_unattended=False`인데,
실제 성격은 N건 순차 실행이다. JSON 덮어쓰기 확인(`trigger/monitor.py:1023`)과 DB 테이블
처리 선택(`:1058-1069`)은 `save_type is None`일 때만 뜨는데, `save_type`은 무인 실행에만
주입되므로(`extract_override`가 `is_unattended`일 때만 채워짐) **선택 수집 N건 중 1번째에서
저장 충돌 모달이 뜨면 나머지는 그 모달을 닫을 때까지 시작되지 않는다.**

**③은 반대로 어긋나 있다.** unattended로 분류돼 0건 시 트레이 알림을 쓰는데
(`trigger/main_window.py:510-515`), 사용자는 방금 버튼을 눌러 화면 앞에 있을 가능성이 높다.
3초짜리 트레이 풍선은 오히려 놓치기 쉽다.

**④는 통보 우선순위가 역전돼 있다.** 트레이 알림이 걸린 유일한 케이스가 "0건"인데, 더
치명적인 DB 저장 실패(`trigger/monitor.py:1086`)·자동 저장 예외
(`trigger/main_window.py:555`)는 로그 한 줄로 끝난다. 로그 뷰어는 별도 다이얼로그라 닫혀
있으면 아무도 못 본다.

## 4. 이슈 후보 (구조적 결함)

아래 4건은 설계 논의 이전에 그 자체로 버그였다. `ISSUES.md` §2 형식(위치/상세/사유·필요
조치)으로 정리했으나, **전부 구현 완료됐으므로 `ISSUES.md` §1(해결됨) 표로 정식 등록하는
것은 별도로 진행이 필요하다**(이 문서 통합 작업에서는 하지 않음).

### 후보 A. `interrupted` 플래그가 "사용자 중단"과 "실행 실패" 두 의미로 오버로드됨 — ✅ 해결(1순위)

- **위치**: `worker.py:144-148`(중단 분기), `:215-220`(`EXECUTOR_STATUS: FAILED` 처리),
  `trigger/main_window.py:173-182`/`482-492`(`_on_finished` interrupted 조기 return)
- **상세**: Scrapy 자체 실행 실패(`ReactorNotRestartable` 등)를 자식이
  `EXECUTOR_STATUS: FAILED`로 보고하면 부모가 `self._running = False`를 세운다
  (`worker.py:219`). 그러면 다음 루프에서 **사용자 중단과 완전히 동일한 분기**로 들어가
  (`worker.py:144-148`) ①큐에 남아 있던 정상 수집 결과가 `_drain_queue()`로 폐기되고,
  ②로그에 사실과 다른 `"사용자에 의해 중단됨"`이 남고, ③`summary["interrupted"]=True`가
  되어 `_on_finished()`가 조기 return하면서 `_mark_schedule_done()`과
  `_consume_pending_queue()`를 모두 건너뛴다. 그 결과 스케줄은 status가 `"실행 중"`으로
  고착돼 앱 재시작 전까지 영구 정지하고, 배치 잔여 태스크는 `_pending_queue`에 남아 있다가
  나중에 다른 작업이 정상 종료될 때 예상치 못한 시점에 실행된다.
- **사유·필요 조치(설계 당시)**: `summary`에 `aborted`(실행 실패) 필드를 `interrupted`
  (사용자 의도)와 분리해 추가하고, `_on_finished()`의 조기 return 분기를 사용자 중단
  전용으로 좁힌다.
- **실제로 한 일**: `worker.py`에 `aborted`/`abort_reason` 필드 신설, `interrupted`와
  상호 배타적으로 계산되도록 수정. `EXECUTOR_STATUS: FAILED` 수신 시 남은 큐를 버리지
  않고 처리하도록 변경. `trigger/main_window.py` 단일·다중 `_on_finished()`에 aborted
  전용 분기를 추가해 스케줄 재무장·대기 큐 소비가 정상 진행되게 함. 자세한 내용은
  Part 2 §7 참고.

### 후보 B. HTTP 200 + 추출 예외가 "성공"으로 집계됨 — ✅ 해결(3순위)

- **위치**: `worker.py:287-320`(`_handle_line` 분류 로직), `engine.py:453-458`
  (`build_failure_item`이 `extract_error`를 세팅하는 지점)
- **상세**: `empty_extract = status_code == 200 and not extracted and not extract_error`
  (`worker.py:289`)이므로, 추출 중 예외가 나 `extract_error`가 채워지면 `empty_extract`는
  False가 된다. HTTP는 200이므로 `elif status_code == 200: level = "ok"`
  (`worker.py:318-319`)로 떨어져 `_errors`에 포함되지 않고 `success`에 산입된다. 로그도
  `log_level = "info"`로 `f"{method} {url}"` 한 줄뿐(`:327-328`)이라 예외 내용이 전혀
  노출되지 않는다. 사이트 구조 변경으로 XPath가 전건 깨져도 세션 요약에는 "성공 N건"으로
  표시된다.
- **사유·필요 조치(설계 당시)**: 분류 조건을 `extract_error`가 있으면 `empty_extract`와
  별도로 `"warn"`(또는 별도 `extract_error` 레벨)로 분리하고, `_errors`에는 포함하지
  않되(응답 자체는 성공) `success`와는 구분되는 집계 축을 둔다.
- **실제로 한 일**: `worker.py::_handle_line()`이 HTTP 200+`extract_error`를
  `empty_extract`와 같은 `"warn"`으로 분류하도록 수정(`_errors`에는 그대로 미포함).
  통계 페이지(`trigger/statistics.py::_outcome()`)는 조사 결과 이미 `extract_error`를
  "데이터 누락"으로 정확히 집계하고 있었음이 확인돼, 실시간 로그·요청 상세 팝업 두 곳만
  고치면 충분했다. 자세한 내용은 Part 2 §7 참고.

### 후보 C. 선택 수집(SELECT_JOB) 순차 실행 중 저장 충돌 모달이 큐를 차단 — ✅ 해결(1·2순위)

- **위치**: `trigger/main_window.py:530-553`(`MainWindowTriggersMulti._on_finished`의
  자동 저장 블록), `trigger/monitor.py:1021-1030`(JSON 덮어쓰기 확인),
  `:1057-1076`(DB 테이블 처리 선택)
- **상세**: `is_unattended = task.get("job") in ("스케줄 실행", BATCH_JOB)`
  (`main_window.py:496`)이라 `SELECT_JOB`은 무인으로 분류되지 않고, `extract_override`도
  `is_unattended`일 때만 주입되므로(`:548`) `save_type is None`이 되어 `_extract_result_table()`
  내부의 두 확인 모달이 그대로 실행된다. `_start_batch()`가 선택된 N건을 순차 실행하는
  구조이므로(`:358-401`), 1번째 저장에서 모달이 뜨면 2번째 이후는 사용자가 그 모달을 닫을
  때까지 시작되지 않는다.
- **사유·필요 조치(설계 당시)**: §6 원칙 2(모달 허용 여부를 job 이름이 아니라 "단건 유인
  실행"인지로 판정)를 적용하면 자동으로 해소된다. 임시 조치로는
  `task.get("batch_meta", {}).get("total", 1) > 1`이면 `SELECT_JOB`도 무인 취급해 저장
  방식을 사전 확정(`schedule_save_type` 없으면 "new" 기본값)하도록 좁힐 수 있다.
- **실제로 한 일**: 1순위에서 우선 `is_sequential_save`라는 임시 변수로 저장 방식만
  사전 확정하도록 좁혀서 급한 불을 껐고, 2순위에서 `_modal_allowed(task)`로 판정 기준
  자체를 통일하면서 이 임시 변수를 완전히 흡수·제거했다. 예상대로 원칙 2 적용만으로
  자동 해소됐다. 자세한 내용은 Part 2 §7 참고.

### 후보 D. 정제 경로에 "EXTRACT 버튼일 때만 팝업" 원칙이 미적용 — ✅ 해결(3순위)

- **위치**: `trigger/monitor.py:967-980`(`_extract_result_table`의 refined 분기),
  `:248-276`(`_run_refine`)
- **상세**: `_extract_result_table(source="refined")`가 아직 정제되지 않았고 `silent=False`면
  내부에서 `self._run_refine()`을 인자 없이 호출한다(`monitor.py:969` 부근 —
  `notify_empty` 파라미터가 이 호출에는 전달되지 않음). `_run_refine()`은 `skip_ui_update`
  기본값이 `False`라서, `_collected_data`가 비어 있으면 `"정제 불가"` 경고
  (`monitor.py:275`)를, 정제 실행 중 예외가 나면 `"정제 오류"` critical
  (`:327`)을 띄운다. 이 폴백 호출은 자동 저장 경로(수동 실행의 refined 자동 저장 등)에서도
  일어날 수 있어, 최근 커밋(`449f190`)과 작업 트리 변경이 세운 "EXTRACT 버튼 클릭 시에만
  팝업" 원칙과 정면으로 충돌한다.
- **사유·필요 조치(설계 당시)**: `_extract_result_table()`에 이미 있는 `notify_empty`
  파라미터를 이 폴백 호출에도 전파하거나(`self._run_refine(skip_ui_update=not notify_empty)`
  등), `_collected_data`가 비어 있고 `notify_empty=False`인 경우엔 폴백 호출 자체를
  생략하고 로그만 남기도록 좁힌다.
- **실제로 한 일**: 설계 제안 그대로 `self._run_refine(skip_ui_update=not notify_empty)`로
  수정. EXTRACT 버튼 클릭 경로(`notify_empty` 기본값 `True`)는 기존과 동일하게 동작하고,
  자동 저장 경로(`notify_empty=False`)에서만 팝업이 로그로 대체됨을 확인했다. 자세한
  내용은 Part 2 §7 참고.

## 5. 참고: 심각도가 감지되지 않거나 트레이 알림이 없는 지점

이 문서 §4의 4건 외에, 설계 단계에서 함께 고려했던 관찰 사항이다.

- **무인 실행의 심각한 실패에 트레이 알림 없음** — ✅ 해결(3순위). 트레이 알림은 "0건"
  하나에만 연결돼 있었으나(`main_window.py:198-203,510-515`), 3순위에서 DB/파일 저장
  실패 시에도 트레이 알림이 뜨도록 추가했다.
- **비모달 지속 상태 부재** — ✅ 해결(2순위). `_update_step_ui()`는 실패해도 그냥
  0(수집 대기)으로 돌아가고, `BLUEPRINT_STATUS_LABELS`(`layout/multi/blueprint_list.py:21`)에는
  `"done"` 키조차 없어 완료/실패가 모두 "대기"로 표시되던 문제. 2순위에서 대시보드
  "실패 배너"와 블루프린트 목록 "실패" 상태(빨간 글씨)를 신설해 해소했다.
- **자식 프로세스 행(hang) 감지 로직 전무** — ❌ 미해결(이번 범위 밖). 전체 수집
  타임아웃도, 마지막 메시지 이후 무응답 워치독도 없다. Selenium 세션이 멈추면 GUI가
  "수집 중"에 영구 고착되고 수동 중지 외 복구 경로가 없다.
- **전역 예외 훅 부재** — ❌ 미해결(이번 범위 밖). `main.py`에 `sys.excepthook` 등이
  없어, Qt 슬롯 안에서 포착되지 않은 예외는 사용자에게 어떤 형태로도 표시되지 않는다.

## 6. 설계 원칙

### 원칙 1 — 모달은 "질문"에만 쓴다 — 🟡 부분 적용(2·3순위, 무인/순차 실행 범위로 한정)

현재 모달 대부분(`"추출 불가"`, `"정제 불가"`, `"수집 결과 없음"`, `"DB 저장 실패"`,
`"정제 오류"`)은 질문이 아니라 통보다. 사용자가 OK를 누르는 것 외에 할 일이 없다면
비모달 채널로 내린다. 진짜 질문(덮어쓰기 확인, DB 테이블 처리 선택)은 **실행 중에 물으면
안 되는 질문**이므로(큐 차단, 후보 C 참고), 스케줄의 `schedule_save_type`처럼 실행 전에
사전 확정한다.

> 질문은 실행 전에, 통보는 실행 후에.

**실제 적용 범위**: 사용자가 명시적으로 "무인/순차 실행만 배너로, 수동 단건 실행은
기존처럼 즉시 모달 유지"로 범위를 좁혔다 — 지켜보고 있는 사용자에게는 즉각적인 팝업
피드백이 더 낫다는 판단. 원칙 원문("질문 아닌 통보는 항상 비모달")보다 좁은 범위로
구현됐다.

### 원칙 2 — 모달 허용 여부를 job 이름이 아니라 실행 성격으로 판정 — ✅ 적용됨(2순위)

지금은 단일/다중이 `is_unattended` 정의를 다르게 쓰고(`main_window.py:188` vs `:496`),
`SELECT_JOB`은 `open_save_path`라는 또 다른 축으로 별도 처리된다(`:550`). job 문자열이
늘어날 때마다 분기가 증식하는 구조다. 이미 존재하는 데이터로 판정을 단순화한다:

```
모달 허용 = 사람이 직접 시작했고(task_nm 없음) AND 단건 실행이다(batch_meta.total <= 1)
```

- 수동 실행 → 허용 (단건, 후속 없음)
- 행 ▶ 개별 실행 → 허용 (`batch_meta.total == 1`)
- 선택/전체 수집 N건 → 차단 (N>1이면 무조건)
- 스케줄 → 차단 (`task_nm` 보유)

job 라벨 4개가 아니라 "단건 유인" vs "그 외" 2분류로 줄어들고, `silent`/`notify_empty`/
`skip_ui_update` 3개로 갈라진 현재 가드를 이 하나로 수렴시킬 수 있다.

**실제로 한 일**: `trigger/common.py::_modal_allowed(task)`로 그대로 구현. 다만 "정제
규칙 강제 적용 여부"는 모달 판정과는 무관한 별개 개념이라 통합하지 않고
`use_fixed_refine_rules`로 분리해 유지했다(선택 수집이 N건이라도 각 블루프린트 화면의
실시간 체크박스 상태는 신뢰할 수 있으므로).

### 원칙 3 — 심각도 3단계로 "멈출 것/기록할 것"을 가른다 — 🟡 부분 적용(색상 단계는 미적용)

| 등급 | 정의 | 판단 기준(예) | 유인 단건 | 순차 실행 | 스케줄(무인) |
|---|---|---|---|---|---|
| 치명(aborted) | 실행 자체가 성립 안 됨 | Scrapy 기동 실패(후보 A), 블루프린트 소실 | 모달 | 배너 + 큐 계속 여부 검토 | **트레이 알림** |
| 실패(failed) | 이번 건 산출물 없음 | 0건, 저장/정제 실패 | 상태 배너 | 배지 + 큐 계속 | **트레이 알림** |
| 열화(degraded) | 산출물은 있으나 품질 저하 | 일부 요청 실패, 추출 예외(후보 B), 규칙 미적용 | 로그 + 행 표식 | 로그 + 행 표식 | 로그만 |

현재는 무인 실행의 "실패" 등급에 트레이 알림이 없다(0건에만 있음). 수집은 됐는데 저장이
안 된 쪽이 더 치명적이므로 이 부분을 뒤집는다.

**실제로 한 일**: "저장 실패 시 트레이 알림 추가"(표의 핵심 요구사항)는 3순위에서
구현됐다. 다만 치명/실패/열화 3단계를 색상·표시 방식으로 세분화하는 것(배너를 등급별로
다른 색으로 칠하는 것 등)은 하지 않았다 — 현재 배너·목록 상태는 실패 전부를 같은
빨간색 하나로만 표시한다.

### 원칙 4 — 순차 실행은 건별 통보 대신 종료 요약 — ✅ 적용됨(3순위)

전체 수집 10건 중 3건이 0건이면 지금은 로그에 흩어진 3줄이 전부다. `_pending_queue`가
빌 때 "10건 중 7건 성공 · 2건 0건 · 1건 저장 실패" 형태의 요약을 한 번 내면 건별 통보보다
유용하고 모달 압력도 준다. `batch_meta`에 이미 index/total이 있어 집계 지점은 확보돼 있다.

**실제로 한 일**: `trigger/main_window.py::_record_batch_outcome()`으로 구현. 다만
"저장 실패"는 별도 범주로 분리하지 않고 "성공/0건/실패(aborted)" 3범주로 좁혔다 — 저장
함수가 성공/실패를 반환하지 않아 구분하려면 반환 계약을 바꿔야 했기 때문. 종료 판정은
`_pending_queue`가 비었는지가 아니라 `batch_meta.index`/`total`로 한다 — 스케줄과 큐를
공유하는 구조라 큐가 비는 시점만으로는 배치 종료를 오판할 수 있음을 확인했기 때문.

- **블루프린트 목록에 "실패" 표시 추가**: 다중 화면의 수집 목록에서, 실패한

  전부 "대기"로만 보여서 구분이 안 됐다.

| `trigger/statistics.py` | 세션 이력에 "실패" 상태 반영 |
| `layout/common.py` | 실패 배너 위젯 신설 |
| `layout/single/dashboard.py` | 실패 배너를 대시보드 화면에 배치 |
| `layout/multi/blueprint_list.py` | 수집 목록에 "실패" 상태·빨간색 표시 추가 |
| `layout/multi/main_window.py` | 배치 결과 집계용 상태 추가 |

(다중 레이아웃 대시보드는 별도 수정 없이 단일 레이아웃 구조를 그대로 물려받아 배너가
자동으로 적용된다.)

## 9. 검증

- 관련 파일 전체가 문법 오류 없이 컴파일되는지 확인했다.
- 모달 허용 판정 함수를 수동 실행/선택 수집(1건, 3건)/전체 수집(1건, 3건)/스케줄 등
  7가지 조합에 직접 대입해 의도한 대로 판정하는지 확인했다.
- 응답 분류 로직(추출 오류/0건/정상/HTTP 오류 4가지 경우)을 가상의 응답 데이터로 직접
  실행해 기존 동작이 깨지지 않았는지 확인했다.
- 배치 요약 로그 로직을 가상의 3건짜리 배치로 실행해 마지막 건에서만 요약이 남고
  집계가 초기화되는지 확인했다.
- 실패 배너 위젯을 실제로 생성해 화면에 나타나고 사라지는지 확인했다.

**한계**: 개발 환경이 WSL(리눅스)이라 실제 Windows GUI에서 클릭해가며 눈으로 확인하는
테스트는 진행하지 못했다. 배너 색상·배치, 트레이 알림 문구, 블루프린트 목록의 빨간
글씨가 실제로 보기 좋게 나오는지는 Windows 환경에서 한 번 확인이 필요하다.

## 10. 이번에 다루지 않은 것 — 다음 후보

- **수동으로 한 건씩 실행할 때의 팝업을 배너로 바꾸는 것** — 지켜보고 있는 사용자에게는
  즉각적인 팝업 피드백이 더 낫다고 판단해, 무인/순차 실행에만 배너를 적용했다(원칙 1).
- **저장 실패를 배치 종료 요약에 별도 항목으로 넣는 것** — 지금은 "성공/0건/실패" 3가지로만
  집계한다. 저장 실패까지 구분하려면 저장 함수의 결과 반환 방식을 바꿔야 한다(원칙 4).
- **심각도를 3단계(치명/실패/열화)로 세분화해 색상까지 나누는 것** — 지금은 실패를
  전부 같은 빨간색 하나로만 표시한다(원칙 3).
- **저장 실패도 대시보드 배너/수집 목록 상태에 반영하는 것** — 트레이 알림까지만
  추가했다.
- **자식 프로세스 행(hang) 감지, 전역 예외 훅** — 이번 범위(수집 결과 통보 방식) 밖의
  별개 견고성 문제라 다루지 않았다(§5 참고).
- **이슈 후보 A~D를 `ISSUES.md` §1(해결됨) 표에 정식 등록하는 것** — 구현은 완료됐지만
  프로젝트 이슈 관리 문서에는 아직 반영하지 않았다.
